# Proposed Phase 14 — Two-Phone Work-Order Coordination & Photo Safety

**Status:** DESIGN RECORDED — NOT AUTHORIZED FOR RUNTIME IMPLEMENTATION OR MERGE OF A LEVEL-3 BUILD.  
**Project:** Original Field Photo Prep (FPP), NOT Field Work Hub (FWH).  
**Working design line:** `docs/two-user-job-safety-plan-20261009`.  
**Baseline:** PR #95 merged into `main` at `b1dbf009c9240b3d70b95629baf049d7e1d4c3bd` (2026-10-10 UTC); operator tested 0.28.7-internal. PR #96 is unrelated Actions hardening.  
**Classification:** this documentation record is Level 1; the planned runtime, data, remote-write and destruction changes are Level 3.  
**Scope boundary:** plan the feature completely before implementation. Do not install new software, mutate Drive, change Supabase, create schema, adjust sharing, enable a service, or change Android behavior under this planning task.

## 1. Problem and operator-approved intent

Two photographers may work on the same address/work order with separate Android phones and local capture/upload queues. Both currently see the same Google Drive company/address/work-order folders through their own deliberately selected Android SAF bindings. **The current Photos list and history are device-local**; seeing zero on another phone does not mean the shared Drive folder has zero.

Concrete dangerous scenario: Phone A uploaded 15 and phone B uploaded 30 to the current work order; 45 are in Drive. Phone A clears/reuses the work order and begins the next occurrence, uploading 10 new photos. Phone B still holds old local uploaded-history entries and attempts a stale Clear & Reuse. Without shared cycle identity, phone B may delete the 10 photos from phone A's **new** occurrence. A common Drive count, another confirmation dialog, a device-local lock, or the single-device safeguards merged in PR #95 do NOT solve this.

Agreed outcome: field-first one/two-person mode per work order; both users see a shared Drive photo total; lead/first-uploader coordination with optional explicit selection; collision-free client numbering starting 001 across both phones; simple finish/handoff; no stale or concurrent phone can destroy next-occurrence photos. Do not add a second photo library, complex team/admin dashboard, constant checkboxes, or duplicate controls.

## 2. Existing invariants and intended small UX

- Preserve the existing Home → Work Orders → Photos/camera → Done → Upload Selected flow, Edit Work Order, Clear & Reuse, company switching, Archive/Reactivate/Delete Address, protected originals, retry/uncertain handling, and operator-selected Android Drive tree.
- Keep **One photographer** as the ordinary default for new/unmanaged work orders. Add exactly one compact selected-work-order control: **Photographers: One / Two**, positioned in the work-order context under its title/status and NOT over any existing action. Do not put a global toggle on Home or displace Edit Work Order / Clear & Reuse. Switching a managed work order back to One does not disable existing shared-cycle safety or revoke old phone state.
- Show **In Drive: N** beside every visible work order on the Work Orders screen, using a fresh read-only SAF/Drive count of direct image/photo children. Counts are **shared Drive counts**, not the local PendingPhotoStore count. The existing Photos screen still separately shows **On this phone** uploaded/ready/failed history; locally waiting photos do not increase In Drive. Unknown, loading, stale, or permission-denied results display **— / Unable to refresh**, NEVER an invented 0. Do not download all photos to count them.
- Refresh counts and shared mode/lead/cycle state when a work order opens, app resumes, upload completes, or mode/lead changes. Prefer quiet foreground refresh and an existing refresh affordance; no unnecessary background polling, new global refresh screen, or reliance on realtime delivery to protect a destructive write. A risky operation still performs an immediate authoritative revalidation.
- In Two mode, normal capture and uploading remain unchanged. Show compact lead/status text (e.g. "Working together · Lead: You" or "Waiting for other phone") only when useful. No repeated prompts per photograph.
- Default lead is the **first device/user with a confirmed successful remote upload in the current cycle** (not first shutter press or upload attempt). At Two-mode enrollment, optionally choose which photographer goes first; that user is the preferred lead and first batch uploader. No selection is required for the automatic default. The choice is shared, versioned and protected against stale devices. After uploads begin, transferring lead requires a safe explicit handoff; no silent lead stealing.
- There is no existing FPP **Finish Job** button to reuse: camera **Done** means only end camera session. For Two mode, introduce at most one scoped **Finish photo work** action in existing work-order actions (not a permanent Home button). It declares the lead is finished with this photo cycle after upload reconciliation, **does not delete photos**, and does not equate to client delivery or FWH admin approval. Clear & Reuse remains the existing separate explicit destructive action. Do not add this new action to One-mode workflow by default.
- Never silently add a step to ordinary single-person photography. Both participants can take photos and queue them offline; remote uploading, finishing, toggles and destructive actions honor shared freshness/reconciliation rules.

## 3. Safety model — shared work-cycle identity, not folder names

The work order remains backed by the **exact selected Drive folder for each phone**. The same physical Drive folder can be recycled, but **each job occurrence has a new opaque cycle UUID and monotonic generation**. A rename alone does not change the cycle. Distinguish: (1) immutable Android per-device provider document ID and tree grant, (2) durable cross-device opaque link identity for the **same shared work-order folder**, and (3) immutable job-cycle identity for the photo set.

**Proposed narrow control plane:** keep photos, company/property/WO folder hierarchy and authoritative remote photo identities in Google Drive. Add only the minimum synchronized coordination state and atomic authorization operations, associated with the original FPP Organization, using FPP's dedicated Supabase installation—not Field Work Hub. No full customer job database, address list, photo contents, thumbnails, or cross-company mirror. Minimal state includes opaque job-link key; current cycle UUID/generation; One/Two mode; active participants and device/session acknowledgement; optional preferred lead / confirmed lead; open/finishing/clearing/recovery status; a durable idempotent photo-UUID-to-shared-sequence reservation for Two mode; operation/fencing token; and a minimal audit trail for recovery. RLS/RPC must derive active Organization membership server-side. Nothing secret/service-role is shipped to Android.

**Important contractual exception, not silently approved:** Current `PROJECT_PROFILE.md`, `CONTRACT.md` and `docs/IDENTITY_MODEL_V1.md` say FPP Supabase is **identity-only** and not a job/photo database. The proposed opaque coordination ledger is still job-related state and therefore needs an **explicit narrow product/architecture contract amendment**, security review and Level-3 approval *before implementation*. Do not disguise this as already allowed. A separate service would increase bloat; reuse the existing backend only if this deliberate, tightly scoped exception is accepted.

**Cross-device binding problem:** Never reuse/copy a phone's Android SAF provider ID to another device. Provisioning must prove both devices selected the **same actual shared Drive folder**, not merely the same visible name. A possible design is a one-time opaque identity marker tied to the exact work-order Drive folder, read by each phone using its own SAF grant and validated against the coordination service. Such a marker is not the live authorization/locking state. **No marker format, location, or write is approved yet.** A marker in a client-shared work-order folder may be visible to the client: the preflight gate must validate a genuinely safe/acceptable placement and conflict behavior; if not viable with SAF, stop and revise the binding architecture before coding or migrating any work. Never treat human-readable folder paths or identical filenames as proof of cross-device identity.

## 4. Strong deletion and upload interlocks

1. All remotely mutating operations on an enrolled/shared work order obtain **online, current-cycle, server-authorized operation rights**. This includes upload/rename, Clear & Reuse, photo-cleanup Archive/Delete, mode/lead changes that affect rights, and finishing. An offline or stale device can safely retain/capture locally but **cannot perform destructive shared Drive writes**, invent a new generation, or upload into a cycle it has not revalidated.
2. For Clear & Reuse, take **exclusive clearing authority** for the exact work-order cycle, and block new uploads/renames/other cleanup across both phones. Resolve local in-flight/UNCERTAIN uploads and receive fresh completion/queue acknowledgements from active participants, or use an explicit owner recovery procedure when the other phone is missing. A missing phone is NOT assumed to have an empty queue; its protected originals stay on that phone, associated with their original cycle.
3. Show the usual property/work order, Drive photo count and selected new date; continue using existing explicit Clear & Reuse confirmation. Revalidate the exact folder identity and old-cycle photo identity snapshot; delete **only confirmed old-cycle photos**, preserve non-image contents, and stop on any unexpected new/untagged/changed photo, changed identity, unreadable or stale provider result. No broad "delete everything visible now" permission from an old photo count.
4. **Complete the remote-photo removal, verify its result, and advance the shared cycle in the correct controlled order before releasing new-cycle upload rights.** The folder keeps its existing provider identity and parent in successful reuse; cycle UUID and sequence restart only on proven completion. An interrupted/uncertain Clear & Reuse enters shared **RECOVERY BLOCKED** state. The system must not hand another actor a fresh lease while an earlier Drive delete could still complete; timeouts alone must never authorize competing deletion/new upload. Resume by verifying real provider state and coordinating/fencing all affected actors, never by blind retry.
5. A phone that wakes with stale uploaded history or an old cycle cannot clear the new cycle or upload old-cycle photos into it. Remote calls must reject its stale cycle/generation regardless of what its local screen or cached count says. Preserve recoverable local originals and clearly identify the affected work order. No silent redirection or deletion. If original-cycle uploads were never committed before rollover, reconcile or explicitly handle them as old-cycle work.
6. **Archive/Delete Address** photo cleanup is also a destructive path. Require compatible shared-cycle protection on every affected enrolled work order (not merely on Clear & Reuse), and block partial unsafe cross-device cleanup. Edit Work Order continues to preserve folder identity and contents, and checks active shared operations before mutation.
7. A successful app-level protocol protects against cooperating, updated FPP clients; it cannot prevent manual deletion in Google Drive, third-party modifications, or an **old app build that lacks the shared checks**. Two mode may be enabled only after both intended phones have installed a compatible guarded build, established their own SAF connection and successfully joined the same job-link state. Warn/block if an unguarded known installation remains active. Do not overclaim protection against untracked older apps or manual Drive changes.
8. The SAF photo delete is not a database transaction. Therefore the architecture preflight must demonstrate a **genuinely safe fencing/recovery sequence** for paused, crashed, timed-out and slow provider operations. A conventional expiring lock + recheck is **not sufficient**; if it cannot prevent old-cycle deletes racing new uploads, the design must be revised before runtime implementation (potentially a different photo-set isolation strategy, which itself requires explicit contract approval). This is an implementation stop gate, not a test to run on real customer photos.

## 5. Numbering and retry ownership

- Desired shared client names: **001, 002, 003...** across both photographers for the same cycle, not each phone starting at 001 or adding another leading zero. Separate work orders/new cycles begin at 001.
- Current `CONTRACT.md` §7 reserves numbers **at capture** on one device. That cannot guarantee unique shared numbering for two offline cameras. In **Two** mode only, the shared sequencer must atomically reserve a durable number for each stable photo UUID **before its upload is attempted**, under current generation and permitted upload order. This deliberately changes Two-mode sequence semantics and needs an explicit approved contract amendment; preserve One-mode capture numbering without regression.
- Prefer one uploader's selected batch first when explicitly chosen, then the other's. Without a choice, serialize competing photo reservations by authoritative server commit order; preserve capture order within each phone's batch. Do not promise cross-phone chronological shutter order.
- Reservation is idempotent by Organization + cycle + photo UUID, including after crash, uncertain result, restart, or reconnect; retries reuse the same intended filename and exact locally persisted device-specific Drive destination. Do not reassign numbers simply because remote acknowledgement was delayed. No knowingly duplicated numbers or remote objects. Consumed reservations may yield a gap after a failed/discarded capture or unresolved upload under existing non-reuse semantics; never close gaps by renumbering confirmed customer photos without separate approval.
- A central sequencer controls logical names; the existing per-device SAF/Drive coordinator remains the owner of actual Drive writes. No server access to client image bytes is needed.

## 6. Startup, offline operation, migration and rollback

- Existing Work Orders remain as they are until explicitly enrolled. Do not turn all historical customer work orders into Two mode or assume they can be safely reconciled from local histories. Migrate an already-used work order only after verified remote identity and settled photo state; otherwise keep it read-only for enrollment and explain the issue.
- Offline: capture and protected local queue continue for a previously validated member within existing auth rules. Shared Drive totals show last verified value as **stale** or **unknown**. Hold upload, role/mode change, finish and all destructive actions until current cycle can be verified online. Do not delete originals or auto-reassign their destination.
- When One mode is selected after Two mode, retain the shared generation and fencing rules on both clients. Switching modes is not a back door to unsafe Clear & Reuse.
- Original Android account/Organization authorization and Drive access remain separate. No second tree is silently selected, no company sharing is modified, and no cross-project backend/organization data is introduced.
- Disable enrollment with a rollout flag if anything goes wrong; **do not** disable safety enforcement for jobs already enrolled. Rollback to a compatible controlled build without clearing app data or downgrading pending cycle state; recover existing photos first. Capture original baseline commit, schema migrations, server rollback and app compatibility matrix before implementation.

## 7. Implementation/checkpoint order (one coherent Level-3 feature)

**Checkpoint A — contract, ownership and concurrency feasibility.** Review precise current file/functions; choose and prove the cross-device link handshake and acceptable marker placement (or explicitly approved alternative); demonstrate race-safe coordinator fencing with real SAF constraints before changing customer paths; approve narrow FPP backend exception, sequence rule and any folder-shape changes. Record Level-3 impact/rollback, security and privacy boundaries, exact one-branch implementation ownership.

**Checkpoint B — shared control plane, enrollment and compatibility gates.** Implement minimal FPP-only coordinated state/RPC, RLS, device participation and client version validation, cycle generation and fail-closed recovery. Never mix with FWH, duplicate client-company data or bypass Drive SAF.

**Checkpoint C — shared count + field UX + sequenced uploads.** Work Orders read-only Drive counts and fresh/unknown presentation, one/two mode, automatic or chosen lead, lead handoff, live/refresh status, idempotent 001 global reservations, captured-photo cycle binding and offline recovery. Preserve original controls and portrait/landscape layout.

**Checkpoint D — protected finish/clear/archive operations.** Finish photo work in Two mode (no deletion), exclusive multi-device Clear & Reuse and Archive/Delete guards, interrupted/UNCERTAIN recovery, old-cycle/photo identity fencing. Preserve existing one-user flow when never enrolled.

**Checkpoint E — verification and rollout.** Build A–D in largest safe automated batches first, then a consolidated disposable two-physical-phone/real Google Drive reality gate and versioned installation. Do not demand repeated confirmation of already-proven observations; the operator's specific "Works"/"Verified" reports count for the exact behavior described. Level-3 implementation merge requires its own operator approval, which is **not** granted by approving this document.

## 9. Explicit boundaries and current disposition

**Not included:** Field Work Hub work assignments/admin approval/delivery; cloud photo storage; changing existing FPP auth/Drive workspace selection; a permanent photo browser; photo download to the other phone; business-wide dashboards; global auto-cleanup; automatic destructive rollover; multi-account user management tiers; subscription/licensing.

**Plan is complete as a product design proposal, not as an implemented feature.** This record identifies two honest preflight architectural gates (per-folder cross-device binding without client-visible leakage, and provably safe operation fencing across device-mediated SAF writes). No implementation authorization is inferred and no new Phase 14 is marked approved until the operator deliberately chooses to start. At that time, complete Checkpoint A and amend conflicting source contracts **before** app/backend code. If either gate fails, revise the architecture instead of guessing or silently weakening the safety promise.
